# Phone finalization: development branch only

## Previous behavior

The original `live-finish` authenticated a player session or verified admin session. An attending, non-waitlisted player could finish within the scoring window without being a match participant; verified admins bypassed attendance and time checks. It used the supplied player ID as `submitted_by`, required `completed`, rejected unresolved tiebreak choice, and stored tiebreak values only for `is_tiebreak`. It inserted the historical score and then deleted the live row as separate database requests. `point_history` supported Undo while the live row remained; it was deleted with that row. The original `live_match_id` foreign key is cleared after cleanup, so it cannot reliably identify later retries.

## Current branch behavior

The phone sends its displayed `expectedVersion` and refuses to finish while local points are pending. The Netlify function validates the existing session, derives `player` or `admin` mode from the verified server-side admin session (never the request body), checks the existing scoring window/attendance where applicable, and calls `public.finalize_live_match_atomic(uuid, integer, uuid, text)`. A stale version produces a structured 409, refreshes the phone and asks the user to review; it is not automatically retried at a newer version. The original separate insert-and-delete finish path was removed.

The service-role-only `SECURITY INVOKER` RPC locks the live row `FOR UPDATE`, checks the trusted caller mode and expected version, inserts from the locked row and deletes the live row in one transaction. `player` requires a yes/not-waitlisted EOI, `watch` additionally requires team membership, and `admin` requires an existing submitted player. Only the server may select admin mode. Retry authorization uses the stored score's event and teams; `source_live_match_id` survives cleanup and identifies the saved result. Newly saved results trigger the existing notification; already-saved or rejected requests do not trigger another.

The Watch API validates a separate hashed, revocable credential, derives the player identity and uses the same helpers plus the RPC in `watch` mode. Local handler tests cover invalid, expired, revoked, replaced and inactive-owner credentials and unrelated participants. Physical Shortcut execution has not been verified.

Local security advisor found no issues; local lint still reports the pre-existing ambiguous `pin_locked_at` reference in `record_player_pin_failure`. Notification transport was stubbed. Sample sizes and local conditions are too small to predict production latency.

## Singles and release risks

Historical migration 001 added two named doubles-only match-score checks that migration 049 did not remove. The local additive migration `20261104163549_allow_singles_score_teams.sql` drops those two checks while retaining the format-aware singles/doubles team-size constraint. Production's actual constraints are unverified; a separately authorized read-only inspection is required before release.

Apply the three draft migrations in timestamp order before deploying code that calls the four-argument RPC. Existing cached phone clients that do not send `expectedVersion` will receive a 400 until updated; coordinate rollout and service-worker refresh. The historical bootstrap in `/private/tmp` was local-only and must never be deployed. Browser/device UI behavior, the exact Shortcuts action compatibility and real notification delivery remain unverified.

Rollback requires redeploying the prior application version while retaining historical scores and the additive columns. The prior application cannot use `source_live_match_id` for its old retry lookup, so its retry behavior after rollback is not equivalent; review and test the rollback procedure before release. Any schema rollback must use a reviewed compensating migration; do not delete saved results or source IDs. Production has not been touched during this work.
